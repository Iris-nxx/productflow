# 产品需求文档（PRD）

## 概述

设计全面、可用于生产的产品需求文档（PRD），把业务愿景和技术落地衔接起来。这个 skill 适用于现代软件系统，确保需求被清楚定义。

## 何时使用

在以下情况使用这个 skill：

- 开始一个新产品或新功能的开发周期
- 把一个模糊想法转成具体的技术规格
- 为 AI 功能定义需求
- 干系人需要一份统一的项目范围「事实来源」
- 用户要求「写一份 PRD」「记录需求」或「规划一个功能」

---

## 操作流程

### 阶段 1：发现（访谈）

在写下 PRD 的任何一行之前，你**必须**向用户提问，补上知识空白。不要自行假设背景。

**要问的内容：**

- **核心问题**：为什么现在要做这个？
- **成功指标**：怎么判断它做成了？
- **约束条件**：预算、技术栈，或截止日期？

### 阶段 2：分析与范围界定

综合用户的输入。识别依赖关系和隐藏的复杂度。

- 梳理**用户流程**。
- 定义**非目标**，以保护时间表。

### 阶段 3：技术起草

使用下面的**严格 PRD 结构**生成文档。

---

## PRD 质量标准

### 需求质量

使用具体、可衡量的标准。避免「快」「容易」或「直观」这类说法。

```diff
# 含糊（不好）
- 搜索应该很快，并返回相关结果。
- 界面必须看起来现代，而且容易使用。

# 具体（好）
+ 对于 1 万条记录的数据集，搜索必须在 200 毫秒内返回结果。
+ 搜索算法在基准评测中必须达到 Precision@10 >= 85%。
+ 界面必须遵循 Vercel/Next.js 设计体系，并达到 100% 的 Lighthouse 无障碍分数。
```

---

## 严格的 PRD 结构

输出**必须**严格遵循以下结构：

### 1. 执行摘要

- **问题陈述**：用 1–2 句话说明痛点。
- **提议方案**：用 1–2 句话说明解决办法。
- **成功标准**：3–5 个可衡量的关键绩效指标（KPI）。

### 2. 用户体验与功能

- **用户画像**：这是给谁用的？
- **用户故事**：`作为一名 [用户]，我希望 [动作]，以便 [收益]。`
- **验收标准**：为每个故事列出「完成」的定义，使用项目符号。
- **非目标**：我们不做什么？

### 3. AI 系统需求（如适用）

- **工具需求**：需要哪些工具和 API？
- **评估策略**：如何衡量输出质量和准确率。

### 4. 技术规格

- **架构概述**：数据流和组件之间如何交互。
- **集成点**：API、数据库和身份认证。
- **安全与隐私**：数据处理和合规要求。

### 5. 风险与路线图

- **分阶段发布**：MVP -> v1.1 -> v2.0。
- **技术风险**：延迟、成本，或依赖项失败。

## 实施指南

### 要做（始终）

- **定义测试**：对于 AI 系统，说明如何测试并验证输出质量。
- **迭代**：先给出草稿，再针对具体章节征求反馈。

### 不要做（避免）

- **跳过发现阶段**：在至少先问 2 个澄清问题之前，绝不要写 PRD。
- **编造约束**：如果用户没有指定技术栈，要提问，或将其标为 `待定`。

## 示例：智能搜索系统

### 1. 执行摘要

**问题**：用户很难在庞大的代码仓库里找到特定的文档片段。
**方案**：一个智能搜索系统，直接给出答案，并附上来源引用。
**成功标准**：

- 搜索时间减少 50%。
- 引用准确率 >= 95%。

### 2. 用户故事

- **故事**：作为一名开发者，我希望用自然语言提问，这样就不用去猜关键词。
- **验收标准**：
  - 支持多轮澄清。
  - 返回带有「复制」按钮的代码块。

### 3. AI 系统架构

- **所需工具**：`codesearch`、`grep`、`webfetch`。

### 4. 评估

- **基准**：用 50 个常见的开发者问题进行测试。
- **通过率**：90% 必须与预期引用一致。
